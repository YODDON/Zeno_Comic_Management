# Missions Module

Five server-authoritative actions: `DailyLogin`, `ChapterReadQualified`, `ComicFollowed`, `ChapterUnlocked`, `WalletTopUpCompleted`. Types: Fixed, Daily, Weekly, Event. Weekly is Monday 00:00 to next Monday 00:00 `Asia/Ho_Chi_Minh`.

## Definition/version and progress
MissionDefinition stable ID; MissionRevision with target, Bonus reward, repeat policy, active period; per user/revision/period MissionProgress. `action_receipts` dedup source event; `progress_actions` dedup relevant subject (chapter, comic or order) within mission/period. A single valid event may contribute to more than one configured Mission. Event-time determines applicable revision, local date and period, not worker processing time. Revisions must not rewrite in-flight progress.

`MissionDefinition.ActiveRevisionId` is authoritative for the current Admin state and the user-facing current Mission list. M02 additionally persists activation history so receipt processing uses the revision that was active at the event's authoritative `OccurredAt`, never the revision that happens to be current when the worker runs. An activation interval is half-open: `ActivatedAt <= OccurredAt < DeactivatedAt`, with a null end for the currently open interval. There is no fallback to `ActiveRevisionId` when no historical interval matches. Each Mission has a monotonic `ActivationSequence`; the row is immutable except for the one-time close of a null `DeactivatedAt`.

Activation/deactivation locks the Mission definition, samples PostgreSQL server time, closes the current interval, inserts the successor interval when activating, updates/clears `ActiveRevisionId`, writes the audit record, and commits atomically. Draft revisions are never selected. Overlapping history is rejected. Repeat-policy values encode the frozen defaults: `OncePerVietnamDate` for DailyLogin and `UniqueSubjectPerPeriod` for subject-bearing actions. Daily periods run from local midnight to local midnight, and weekly periods from Monday 00:00 to the next Monday 00:00 in `Asia/Ho_Chi_Minh`; Fixed/Event use the selected revision's half-open effective window. The historical revision must also contain `OccurredAt` in its effective window. Deactivation creates a gap until another revision is activated; events in that gap do not progress a Mission.

M01 consumes five server events into `action_receipts`: Identity `UserLoggedIn`, qualified-read, follow, unlock and fulfilled-TopUp. Identity emits one stable `loginId` with the server-authoritative login timestamp in the same persistence boundary as a successful Google sign-in. All source-event producers normalize event time to PostgreSQL `timestamptz` microsecond precision before serializing payload and envelope. Receipt insertion and infrastructure processed-message marking share the outbox worker transaction. Receipt source identity is semantic where the producer provides one (login, ReadingSession, ChapterUnlock or PaymentOrder); Follow uses the unique outbox message because an unfollow/refollow is a new occurrence. Each receipt persists a lowercase SHA-256 fingerprint of the canonical typed event payload, binding every authoritative event field. Duplicate delivery is idempotent on `(sourceEventId, sourceEventType)` only when the full fingerprint and authoritative receipt fields match; identity reuse with any different semantic payload fails closed and is not marked processed. `occurred_local_date` is derived by the domain from `OccurredAt` in `Asia/Ho_Chi_Minh`, never supplied by callers. A receipt starts `Pending`; M02 owns progress processing and transition to `Processed`.

Admin configuration is exposed by `/api/v1/admin/missions`: list/get definitions, create a definition, append a revision, activate one selected revision and deactivate the definition. Every route requires the Admin policy; unsafe methods require antiforgery validation, mutations are audited, share a 20 requests/minute/Admin fixed-window limit, and activation/deactivation use the definition version for optimistic concurrency. Request enums are string-only.

M02's persistent worker processes `Pending` receipts. It locks or creates the User Wallet first, then locks the receipt, then locks candidate Mission definitions in ID order. This lock order is shared by Mission workers so concurrent rewards for one User serialize on the Wallet row. A processing failure rolls back progress, counter, Wallet, ledger, reward and outbox together; the receipt remains `Pending` for retry. A successfully evaluated receipt becomes `Processed` even when no historical activation matches. User read APIs are `/api/v1/missions`, `/api/v1/missions/daily-limit`, and cursor-based `/api/v1/missions/rewards`; they never grant or claim a reward.

## Default repeat semantics
DailyLogin one per VN day; ChapterReadQualified one unique chapter per mission period; ComicFollowed one unique Comic per mission period even if unfollow/refollow; ChapterUnlocked one unique Chapter/user event; WalletTopUpCompleted one unique fulfilled PaymentOrder. Policy may constrain target/cooldown; don't invent undisclosed farming allowances.

## Grant
Reward at most 300 Bonus Coins per VN local event day/user. Lock `daily_counters(user_id,local_date)` and transact reward decision, counter, Wallet Bonus balance, immutable `MissionReward/RewardGrant` ledger entry and success outbox atomically. A granted reward must have exactly one positive Bonus/Available ledger entry equal to the configured reward and bound back to the reward ID; persistence rejects drift. If a grant would push above 300, persist `DeniedDailyCap` and grant **0**, with no Wallet operation, partial grant or carryover. A completed mission is not always a rewarded mission. Mission reward >300 cannot ever be paid; reject the revision in MVP. Worker delay never changes the event date/revision and never forfeits a legitimate reward merely because processing is late.

## Acceptance
Concurrent multi-mission grants never exceed 300; delayed 23:59 event counts prior local date, dedup by subject; duplicate processed message does not recredit; revision effective at occurredAt.
