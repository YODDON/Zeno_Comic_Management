# Missions Module

Five server-authoritative actions: `DailyLogin`, `ChapterReadQualified`, `ComicFollowed`, `ChapterUnlocked`, `WalletTopUpCompleted`. Types: Fixed, Daily, Weekly, Event. Weekly is Monday 00:00 to next Monday 00:00 `Asia/Ho_Chi_Minh`.

## Definition/version and progress
MissionDefinition stable ID; MissionRevision with target, Bonus reward, repeat policy, active period; per user/revision/period MissionProgress. `action_receipts` dedup source event; `progress_actions` dedup relevant subject (chapter, comic or order) within mission/period. A single valid event may contribute to more than one configured Mission. Event-time determines applicable revision, local date and period, not worker processing time. Revisions must not rewrite in-flight progress.

M01 stores definitions as `Draft` or `Active`; `MissionDefinition.ActiveRevisionId` is the only authoritative runtime selection. It points to one append-only revision owned by that definition. Draft/unactivated revisions are never selected, overlapping draft windows are harmless, and an active revision outside its half-open effective window makes the Mission ineligible without falling back to another revision. Repeat-policy values encode the frozen defaults: `OncePerVietnamDate` for DailyLogin and `UniqueSubjectPerPeriod` for subject-bearing actions. Daily periods run from local midnight to local midnight, and weekly periods from Monday 00:00 to the next Monday 00:00 in `Asia/Ho_Chi_Minh`; Fixed/Event use the selected revision's half-open effective window. Revision selection and window membership use the action's authoritative UTC `OccurredAt` (`effectiveFrom <= OccurredAt < effectiveUntil`). Deactivation clears `ActiveRevisionId` and returns the definition to `Draft`; revisions remain immutable.

M01 consumes five server events into `action_receipts`: Identity `UserLoggedIn`, qualified-read, follow, unlock and fulfilled-TopUp. Identity emits one stable `loginId` with the server-authoritative login timestamp in the same persistence boundary as a successful Google sign-in. Receipt insertion and infrastructure processed-message marking share the outbox worker transaction. Receipt source identity is semantic where the producer provides one (login, ReadingSession, ChapterUnlock or PaymentOrder); Follow uses the unique outbox message because an unfollow/refollow is a new occurrence. Duplicate delivery is idempotent on `(sourceEventId, sourceEventType)` only when the authoritative user, subject and timestamp are identical; identity reuse with a different payload fails closed and is not marked processed. `occurred_local_date` is derived by the domain from `OccurredAt` in `Asia/Ho_Chi_Minh`, never supplied by callers. A receipt starts `Pending`; M02 owns progress processing and transition to `Processed`.

Admin configuration is exposed by `/api/v1/admin/missions`: list/get definitions, create a definition, append a revision, activate one selected revision and deactivate the definition. Every route requires the Admin policy; unsafe methods require antiforgery validation, mutations are audited, and activation/deactivation use the definition version for optimistic concurrency. M01 does not implement Mission progress, reward calculation or claim APIs.

## Default repeat semantics
DailyLogin one per VN day; ChapterReadQualified one unique chapter per mission period; ComicFollowed one unique Comic per mission period even if unfollow/refollow; ChapterUnlocked one unique Chapter/user event; WalletTopUpCompleted one unique fulfilled PaymentOrder. Policy may constrain target/cooldown; don't invent undisclosed farming allowances.

## Grant
Reward at most 300 Bonus Coins per VN local day/user. Lock `daily_counters(user_id,local_date)` and transact reward grant, Bonus Wallet entry, outbox/inbox dedup atomically. If grant would push above 300, mark `DeniedDailyCap` and grant **0**, no partial/carryover. A completed mission is not always a rewarded mission. Mission reward >300 cannot ever be paid; reject definition in MVP. Worker delay never automatically forfeits legitimate reward; retry persistently, expose alerts and manual operational recovery.

## Acceptance
Concurrent multi-mission grants never exceed 300; delayed 23:59 event counts prior local date, dedup by subject; duplicate processed message does not recredit; revision effective at occurredAt.
