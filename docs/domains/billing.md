# Billing Module

Own PaymentOrders, SePay transaction ingestion, webhook deliveries, RefundRequests, protected bank recipients, manual transfer records. Provider payment verification and domain fulfillment are separate statuses. Orders types TopUp/VipPurchase; VND integer snapshots. TopUp valid range 10,000–2,000,000 VND, step 1,000; Paid Coins = VND/10.

TopUp PaymentOrder timestamps are server-owned. The default TTL is 30 minutes and is configurable through `Billing:TopUpOrderTtlMinutes` with fail-fast positive-value validation. PostgreSQL time is sampled only after entering the idempotency critical section. Processing a Pending order at `serverNow >= expiresAt` persists `Expired` and `expiredAt`; the transition is monotonic and is never reversed by clock skew. Expiry does not release `(User,TopUp,Idempotency-Key)`: same key and canonical amount replays the original order, including an expired order; a different amount conflicts; a new operation requires a new key.

B01 limits TopUp creation to 10 requests/minute/authenticated User and owns order creation, validation, idempotency, expiry and persistence integrity. B02 owns authenticated SePay delivery ingestion and durable provider-event deduplication. B03 owns exact TopUp matching and exactly-once fulfillment. Checkout/QR generation and actual project-account SePay Test-mode behavior remain **Verification Required**.

## Payment
Unique order code and provider transaction identity. B02 reads the exact raw JSON body, verifies `X-SePay-Signature` as HMAC-SHA256 over `{X-SePay-Timestamp}.{rawBody}`, rejects timestamps outside the configurable five-minute default window, and checks the configured receiving account. The endpoint is disabled until a secret and receiving account are configured and is limited by remote address (120 requests/minute by default). Authenticated incoming events are normalized into `provider_transactions`; every accepted, duplicate or reconciliation-required delivery is recorded in `webhook_deliveries` in the same PostgreSQL transaction. `(provider, provider_transaction_id)` is the financial deduplication key and a same-ID/different-payload event is fail-closed into reconciliation. Raw payloads, secrets and full account numbers are not persisted.

B03 extends the B02 transaction boundary through TopUp matching and fulfillment. After provider deduplication and deterministic financial locks (Wallet, Paid lots, then PaymentOrder recheck), PostgreSQL `clock_timestamp()` is the authoritative processing time. Auto-fulfillment requires a still-Pending TopUp, `serverNow < expiresAt`, exact VND amount and no prior fulfillment state. The same transaction marks the order `Succeeded`, marks the provider transaction `Fulfilled`, credits Paid available balance, creates exactly one PaidCoinLot, appends one `TopUpCredit` ledger operation/entry and enqueues `Billing.WalletTopUpCompleted.v1`.

Expiry is fail-closed. If the order is already Expired or `serverNow >= expiresAt`, B03 persists the monotonic Expired transition and provider reconciliation reason `LatePayment`, with no Wallet credit, PaidCoinLot, ledger entry or success outbox. Provider `occurredAt` remains audit evidence only and cannot override expiry, including when it predates `expiresAt`. Unknown code, wrong amount, non-TopUp order or a second provider payment for an already fulfilled order is retained as reconciliation evidence and acknowledged without credit. Exact provider replay returns the authoritative fulfilled/reconciliation outcome and creates only another delivery record. Frontend redirect or browser status is never payment proof.

The documented adapter and fulfillment behavior is covered by fixtures and PostgreSQL transaction/concurrency tests. An actual project-owned SePay Test-mode delivery/retry trace remains **Verification Required**; the adapter stays disabled by default and B03 must not be represented as production-verified without that evidence.

## Refund rules
User requests only full original TopUp ≤7 days after verified paidAt, fee 5%, one request per TopUp even if Rejected. Collect bank recipient on request; no reservation until Admin approve. At approve atomically validate full original PaidCoinLot is available (`spent=refunded=reserved=0`), then reserve all. No Bonus/other lot substitution. Admin performs bank transfer externally, records reference/evidence. `NeedsReconciliation` retains reserve; confirmed successful transfer -> Completed and Wallet refund debit; confirmed failed -> Released. No automatic bank payout.

## Privacy
Encrypt recipient account number/holder, track key versions, mask in list/log/audit; restrict Admin visibility. Legal/privacy/retention validation before production.

## Acceptance
B03 task acceptance requires: exact amount/code matching, authoritative processing-time expiry, one PostgreSQL transaction for order/provider/Wallet/lot/ledger/outbox, duplicate and concurrent delivery evidence proving exactly one credit, mismatch/late evidence proving zero credit, and rollback evidence proving no partial financial state. Production release additionally requires the external SePay verification gate described above.
