# Physical ERD — Field-level Blueprint (unmigrated)

**Status:** field-level blueprint; SQL migrations, FKs, physical indexes and full OpenAPI need implementation verification. Names below are canonical unless explicitly marked proposed. Types: UUID IDs, `timestamptz` UTC, `bigint` money/coins, `version bigint` on mutable aggregates. String statuses validated in application and with CHECK where stable.

## Identity and Catalog
- `identity.users`: `id uuid PK`, `display_name varchar(120) NOT NULL`, `email varchar(320)`, `avatar_url text NULL`, `role varchar(16)`, `status varchar(24)`, `created_at`, `updated_at timestamptz`, `version bigint`.
- `identity.google_identities`: `user_id uuid FK`, `google_subject varchar(255) UNIQUE NOT NULL`, `linked_at timestamptz`.
- `catalog.comics`: `id uuid PK`, `slug varchar(200) UNIQUE`, `title`, `description`, `series_status`, `publication_status`, `first_published_at timestamptz NULL`, `cover_asset_id`, `default_price_coins bigint CHECK>=0`, `default_vip_eligible boolean`, `version`, timestamps; public-list index `(publication_status,updated_at DESC,id DESC)`.
- `catalog.chapters`: `id uuid PK`, `comic_id uuid FK`, `chapter_label varchar(120)`, `sort_order integer`, `price_override_coins bigint NULL CHECK>=0`, `vip_override boolean NULL`, `publication_status`, `published_at timestamptz NULL`, `version`, timestamps; unique `(comic_id,sort_order)`; CHECK Published implies non-null `published_at`; public-list index `(comic_id,publication_status,sort_order,id)` and reader-update index `(comic_id,publication_status,published_at DESC,id DESC)`.
- `catalog.chapter_pages`: `id uuid PK`, `chapter_id uuid FK`, `page_order integer`, `cloudinary_public_id text`, `asset_status varchar(24)` (`Pending|Ready`), `upload_fingerprint varchar(80)`, `upload_created_at timestamptz`, `width integer`, `height integer`; unique `(chapter_id,page_order)`, unique `cloudinary_public_id`, and operational index `(asset_status,upload_created_at)`. New intents use `sha256:<lowercase hex>`; migrated pre-fingerprint rows retain a `legacy:<page-id>` sentinel rather than losing data. `Pending` is a durable upload intent with zero dimensions; `Ready` requires positive width/height and is the only status valid for publication.
- `catalog.genres(id,slug UNIQUE,name)`, `authors(id,name)`, `translation_groups(id,name)`; join tables composite PK `(comic_id,dimension_id)`.
- `catalog.featured_comics`: `comic_id uuid PK FK`, `display_order integer UNIQUE CHECK 1..5`; max five and Published eligibility via transactional command. `catalog.featured_configuration` is the singleton (`id=1`) optimistic-concurrency aggregate with `version` and `updated_at`; reorder deletes/inserts positions and advances the version atomically.

## Reading and Interaction
- `reading.reading_sessions`: `id uuid PK`, `user_id uuid FK`, `comic_id uuid FK`, `chapter_id uuid FK`, `started_at timestamptz`, `expires_at timestamptz CHECK expires_at = started_at + 30 minutes`, `last_activity_at timestamptz NULL`, `last_activity_was_ready boolean`, `active_duration_ms bigint CHECK 0..1800000`, `current_page_order integer NULL`, `current_page_offset_ratio numeric NULL CHECK 0..1`, `max_progress_basis_points integer CHECK 0..10000`, `manifest_revision varchar(64)`, `manifest_page_count integer CHECK>=1`, `last_accepted_sequence bigint`, `last_request_fingerprint varchar(64) NULL`, `minimum_progress_basis_points integer`, `minimum_active_duration_ms bigint`, `policy_revision varchar(32)`, `qualified_at timestamptz NULL`, `status Active|Qualified`, `version bigint`; indexes `(user_id,started_at DESC,id DESC)`, `(chapter_id,qualified_at)`, and `comic_id`. Sequence/fingerprint and qualification/state consistency are database CHECK constrained.
- `reading.reading_progress`: composite PK `(user_id,comic_id)`, `last_chapter_id uuid FK`, `last_page_order integer CHECK>=1`, `last_page_offset_ratio numeric CHECK BETWEEN 0 AND 1`, `accepted_max_progress_basis_points integer CHECK BETWEEN 0 AND 10000`, `last_read_at timestamptz`, `source_session_id uuid FK`, `source_session_started_at timestamptz`, `version bigint`; indexes `(user_id,last_read_at DESC)`, `comic_id`, `last_chapter_id`, and `source_session_id`. Source session/start prevents an older parallel tab from overwriting newer progress; accepted maximum progress is copied from the authoritative R02 session whenever its heartbeat is persisted.
- `reading.chapter_unlocks`: immutable `id uuid PK`, `user_id uuid FK`, `chapter_id uuid FK`, `quote_id uuid UNIQUE`, `wallet_operation_id uuid UNIQUE`, `price_paid_coins bigint CHECK>0`, `bonus_spent_coins bigint CHECK>=0`, `paid_spent_coins bigint CHECK>=0`, `wallet_paid_available_after bigint CHECK>=0`, `wallet_bonus_available_after bigint CHECK>=0`, `unlocked_at`; CHECK `price_paid_coins = bonus_spent_coins + paid_spent_coins`; unique `(user_id,chapter_id)`. Composite restrictive FKs bind the quote to the same User/Chapter and the Wallet operation to the same User. A deferred financial-integrity constraint trigger additionally requires `WalletOperation(OperationType=ChapterUnlock,SourceType=ReadingUnlock,SourceId=chapter_unlock.id)`, matching Bonus/Paid debit-ledger totals, and Paid allocation totals equal to `paid_spent_coins`; legacy rows are validated before the guard is installed. The quote reference permanently protects a consumed quote from retention cleanup; an append-only database guard rejects UPDATE/DELETE. The unique quote and Wallet-operation indexes cover their ownership-FK left prefixes, so no redundant composite indexes are retained.
- `reading.chapter_unlock_quotes`: `id uuid PK`, `user_id uuid FK`, `chapter_id uuid FK`, `base_price_coins bigint`, `vip_discount_applied boolean`, `vip_discount_percent integer`, `final_price_coins bigint`, `bonus_to_spend bigint`, `paid_to_spend bigint`, `price_revision char(64)`, `created_at`, `expires_at CHECK = created_at + 5 minutes`; indexes `(user_id,expires_at)` and `(chapter_id,expires_at)`. Rows are immutable pricing snapshots, never reserve funds, and CHECK constraints enforce the fixed 20% round-up calculation plus non-negative balance estimates. UPDATE is forbidden. An expired quote may be deleted only after `expires_at + 30 days`; U01 adds no cleanup worker, and U02 must add a restrictive reference so consumed quotes cannot be removed.
- `reading.comic_follows`: composite PK `(user_id,comic_id)`, `followed_at timestamptz`; restrictive FKs to `identity.users` and `catalog.comics`; keyset index `(user_id,followed_at DESC,comic_id DESC)` plus `(comic_id)` for reverse lookup. The first insert and `Reading.ComicFollowed.v1` outbox row are atomic; unfollow deletes only the ownership row.
- `interaction.comic_ratings`: composite PK `(user_id,comic_id)`, restrictive FKs to `identity.users` and `catalog.comics`, `stars smallint CHECK 1..5`, `created_at`, `updated_at CHECK updated_at>=created_at`; reverse aggregate index `(comic_id)`. PUT uses PostgreSQL upsert under a shared Comic row lock after rechecking the common public-Catalog visibility predicate, so concurrent requests preserve one rating per User/Comic. Public rating and Comic Detail reads use the shared Catalog predicate within one PostgreSQL repeatable-read snapshot, preventing mixed visibility/aggregate results during publication transitions.
- `interaction.comments`: `id uuid PK`, restrictive `user_id` FK, nullable restrictive Comic/Chapter FKs, restrictive self `parent_id` FK, `body varchar(2000)`, `status Visible|Hidden|Deleted`, `created_at`, `updated_at`, optimistic `version`; CHECK exactly one non-empty Comic/Chapter target, nonblank body, monotonic timestamps/version and parent not self. Creation locks in Catalog order (Comic, optional Chapter, readiness pages, optional parent), then revalidates public exposure and reply invariants before insert. Read indexes are `(comic_id,parent_id,created_at,id)`, `(chapter_id,parent_id,created_at,id)`, `(parent_id,created_at,id)`, descending `(created_at,id)` and `(status,created_at,id)` plus the User FK index. Public and Admin paged reads use one repeatable-read snapshot. Deleted is terminal; Admin Hidden->Visible restore and its redacted audit row commit atomically.

## Billing and Refund
- `billing.payment_orders`: `id uuid PK`, `user_id uuid FK`, `order_code varchar(64) UNIQUE`, `order_type varchar(32)`, `amount_vnd bigint CHECK>0`, `paid_coins_snapshot bigint NULL`, `vip_plan_id uuid NULL FK membership.vip_plans`, `vip_duration_hours_snapshot integer NULL`, `vip_discount_percent_snapshot integer NULL`, `provider varchar(32)`, `provider_payment_status varchar(32)`, `fulfillment_status varchar(32)`, `idempotency_key varchar(200)`, `request_fingerprint varchar(64)`, `order_status Pending|Expired|Succeeded`, `expires_at timestamptz CHECK expires_at>created_at`, `expired_at timestamptz NULL`, `verified_paid_at NULL`, `fulfilled_at NULL`, `created_at`, `version`. Unique `(user_id,order_type,idempotency_key)` permanently retains operation identity; alternate keys `(id,user_id)` and `(id,user_id,order_type)` support owned references. Type CHECK requires exact TopUp snapshots or a VipPurchase snapshot with 720 hours/20%; the lifecycle CHECK binds Pending to pending/not-started/null success timestamps, Expired to monotonic `expired_at>=expires_at`, and Succeeded to verified/fulfilled/non-null success timestamps. PostgreSQL time is sampled after locks and permits Pending→Succeeded only before expiry. TopUp TTL is `Billing:TopUpOrderTtlMinutes`; VIP TTL is independently `Membership:VipOrderTtlMinutes`; both default to 30.
- `billing.provider_transactions`: `id uuid PK`, `provider varchar(32) CHECK SePay`, `provider_transaction_id varchar(128)`, `payload_fingerprint varchar(64)`, `amount_vnd bigint CHECK>0`, `direction Incoming|Outgoing`, `payment_code varchar(64) NULL`, `account_number_last4 varchar(4)`, `reference_code varchar(128) NULL`, `matched_order_id uuid NULL FK RESTRICT`, `occurred_at`, `verified_at`, `processing_status Received|ReconciliationRequired|Fulfilled`, `reconciliation_reason varchar(64) NULL`; unique `(provider,provider_transaction_id)`. `Fulfilled` requires a matched order and no reconciliation reason; reconciliation requires a reason and may retain the matched order. `occurred_at` is evidence only and cannot override TopUp or VipPurchase expiry.
- `billing.webhook_deliveries`: `id uuid PK`, `provider_transaction_id uuid FK RESTRICT` (effective non-null via CHECK), `received_at`, `auth_verified boolean CHECK TRUE`, `payload_reference varchar(64)` (SHA-256), `delivery_reference varchar(128) NULL`, `processing_result Accepted|Duplicate|ReconciliationRequired`, `error_code varchar(64) NULL`; a row is written for each authenticated delivery in the same transaction as provider-event ingestion. Financial deduplication is exclusively the provider transaction alternate key, never delivery identity.
- `billing.refund_requests`: `id uuid PK`, `payment_order_id uuid UNIQUE`, `user_id`, `payment_order_type='TopUp'`, `reason varchar(1000)`, `original_amount_vnd bigint`, `fee_amount_vnd bigint CHECK = original*5/100`, `net_refund_vnd bigint CHECK = original-fee`, `required_recovery_coins bigint CHECK>0`, `status varchar(40)`, `idempotency_key varchar(200)`, `request_fingerprint char(64)`, `request_fingerprint_version varchar(40)`, `requested_at`, `reviewed_by/at NULL`, `approved_by/at NULL`, `completed_by/at NULL`, `decision_reason NULL`, `version`; unique `(user_id,idempotency_key)` and at most one request/order even when rejected. Composite snapshot FKs bind `(payment_order_id,user_id,payment_order_type,original_amount_vnd)` to the authoritative TopUp order and `(payment_order_id,user_id,payment_order_type,required_recovery_coins)` to the exact original PaidCoinLot. The single-column unique order index covers the left prefix, so the two redundant child composite FK indexes are absent from both EF metadata and PostgreSQL. A database guard rejects deletion and any update to the identity, reason, amounts, idempotency/fingerprint/version or request-time snapshot; only explicit later lifecycle fields remain mutable for RF02/RF03.
- `billing.refund_recipients`: `id uuid PK`, `refund_request_id uuid UNIQUE FK RESTRICT`, `bank_code`, non-empty `account_number_encrypted bytea`, non-empty `account_holder_encrypted bytea`, `account_number_last4 varchar(4)`, `account_number_masked`, `account_holder_masked`, `encryption_key_version`, `created_at`. Plain account number/holder never enter database columns or response contracts. The row is immutable and cannot be deleted independently after insert; retention/purge requires a separately approved workflow.
- `billing.refund_transfer_records`: `id uuid PK`, `refund_request_id uuid UNIQUE`, `user_id`, normalized nonblank `bank_reference varchar(128) UNIQUE`, `amount_vnd bigint CHECK>0`, nonblank `evidence_reference varchar(500)`, `status ReportedSucceeded|ReportedFailed|NeedsReconciliation|VerifiedSucceeded|VerifiedFailed`, `recorded_by/at`, nonblank record `idempotency_key` plus lowercase 64-hex fingerprint, `verified_by/at NULL`, `confirmation_note NULL`, verification idempotency/fingerprint and `resolution_operation_id NULL UNIQUE`. Verified states require nonblank trimmed confirmation/key, lowercase 64-hex fingerprint, a resolution operation and `verified_at >= recorded_at`; reported states require all verification columns null. Composite restrictive FKs bind the request and resolution operation to the same owner. Core evidence is immutable; it may transition exactly once from a reported success/failure to its matching verified state. Unknown evidence is never verified automatically and keeps the reservation until explicit Complete or Release reconciliation.

## Wallet
- `wallet.wallets`: `user_id uuid PK FK`, `paid_available bigint DEFAULT 0 CHECK>=0`, `paid_reserved bigint DEFAULT 0 CHECK>=0`, `bonus_available bigint DEFAULT 0 CHECK>=0`, `version`, timestamps.
- `wallet.paid_coin_lots`: `id uuid PK`, `user_id uuid FK`, `topup_order_id uuid UNIQUE`, `topup_order_type varchar(32) CHECK='TopUp'`, composite FK `(topup_order_id,user_id,topup_order_type)` to `billing.payment_orders(id,user_id,order_type)`, `granted_coins bigint CHECK>0`, **`spent_coins bigint DEFAULT 0`, `refunded_coins bigint DEFAULT 0`, `reserved_coins bigint DEFAULT 0`**, all >=0, `created_at`, `version`, CHECK `granted_coins >= spent_coins + refunded_coins + reserved_coins` using numeric casts to avoid arithmetic overflow. This validated relation enforces ownership and prevents VIP orders from backing a PaidCoinLot. The B03 migration backfills valid B01 lots to `TopUp` and fails with an explicit reconciliation precondition instead of silently dropping or misclassifying unmatched legacy lots.
- `wallet.wallet_operations`: `id uuid PK`, `user_id uuid FK`, `operation_type`, `source_type`, `source_id uuid`, `idempotency_key NULL`, `created_at`; unique `(operation_type,source_type,source_id)` for one-shot business operations and partial unique `(user_id,operation_type,idempotency_key) WHERE idempotency_key IS NOT NULL`; separate phases have distinct operation types. Rows are append-only through application and database guards.
- `wallet.wallet_entries`: `id uuid PK`, `operation_id uuid`, `user_id uuid FK`, `coin_type` Paid/Bonus, `bucket` Available/Reserved, `delta_coins bigint NOT NULL CHECK<>0`, `leg_order integer CHECK>=1`, `created_at`; composite FK `(operation_id,user_id)` preserves operation ownership, unique `(operation_id,leg_order)`, cursor index `(user_id,created_at DESC,id DESC)`. Rows are append-only through application and database guards; Bonus cannot use the Reserved bucket.
- `wallet.wallet_allocations`: `id uuid PK`, `operation_id uuid FK`, `paid_coin_lot_id uuid FK`, `amount_coins bigint CHECK>0`, `created_at`; unique `(operation_id,paid_coin_lot_id)`.
- `wallet.coin_reservations`: `id uuid PK`, `refund_request_id uuid UNIQUE`, `user_id uuid`, `paid_coin_lot_id uuid`, `wallet_operation_id uuid UNIQUE`, `approved_by uuid FK`, `idempotency_key varchar(200)`, `request_fingerprint char(64)`, `amount_coins bigint CHECK>0`, immutable approval-result fields `approval_result_status='RecoveryReserved'`, `approval_result_version`, `approval_result_reviewed_by/at`, `approval_result_decision_note`, lifecycle `status` Reserved/Consumed/Released, `created_at`, `resolved_at NULL`; unique `(approved_by,idempotency_key)`. Composite restrictive FKs bind the same owner across RefundRequest, exact PaidCoinLot and WalletOperation. The RF02 deferred integrity guard requires the request lifecycle/amount, original-lot linkage, `RefundReserve/RefundRequest` operation source, exactly two Paid ledger legs (`Available=-amount`, `Reserved=+amount`), exact original-lot reserve and aggregate Wallet/lot/ledger Paid Available/Reserved totals to agree at commit. Snapshot/idempotency/result fields are immutable and rows cannot be deleted; RF03 alone may resolve status/time through its explicit workflow.
  RF03 binds a consumed/released reservation to exactly one transfer record and one `RefundComplete`/`RefundRelease` operation. Deferred payout integrity checks require the transfer outcome, request/reservation lifecycle, exact lot counters and resolution ledger legs to agree at commit.

## Membership and Missions
- `membership.vip_plans`: `id uuid PK`, `code varchar(64) UNIQUE`, `name varchar(120)`, `price_vnd bigint CHECK>0`, `duration_hours integer CHECK=720`, `discount_percent integer CHECK=20`, `is_active boolean`, `version CHECK>=1`, `updated_at`; one active plan is enforced by a filtered unique index. V01 seeds the initial 29,000 VND plan.
- `membership.vip_subscriptions`: `user_id uuid PK FK identity.users`, `expires_at timestamptz`, `last_fulfilled_at`, `version CHECK>=1`; CHECK requires `expires_at > last_fulfilled_at`.
- `membership.vip_transactions`: `id uuid PK`, `payment_order_id uuid UNIQUE`, `user_id uuid`, `subscription_version bigint CHECK>=1`, `payment_order_type varchar(32) CHECK='VipPurchase'`, `previous_expiry NULL only at version 1`, `effective_start`, `new_expiry`, `duration_hours CHECK=720`, `fulfilled_at`, `created_at`; unique `(user_id,subscription_version)` is the authoritative transaction order, composite FK `(payment_order_id,user_id,payment_order_type)` enforces order ownership/type, and a database trigger makes rows append-only. Timeline CHECK requires `new_expiry = effective_start + duration` and fulfillment-consistent timestamps. The complete consecutive version/expiry chain must match `vip_subscriptions.version/expires_at` before another fulfillment.
- `missions.mission_definitions`: `id uuid PK`, `code varchar(80) UNIQUE`, `name`, `description`, `action_type` (`DailyLogin|ChapterReadQualified|ComicFollowed|ChapterUnlocked|WalletTopUpCompleted`), `cycle_type` (`Fixed|Daily|Weekly|Event`), `status` (`Draft|Active`), `active_revision_id uuid NULL`, `created_at`, `version >= 1`. `active_revision_id` is the current Admin/UI authority. Active rows must reference a revision owned by the same definition, and a trigger revalidates ownership plus action/repeat-policy compatibility when either `active_revision_id` or `action_type` changes.
- `missions.mission_revisions`: `id uuid PK`, `mission_id uuid FK RESTRICT`, `revision_number integer CHECK>0`, `target_count integer CHECK>0`, `reward_bonus_coins bigint CHECK BETWEEN 1 AND 300`, `repeat_policy` (`OncePerVietnamDate|UniqueSubjectPerPeriod`), `effective_from`, `effective_until NULL` with a valid half-open window, `configuration_snapshot jsonb object`; unique `(mission_id,revision_number)`. Rows are append-only; activation enforces DailyLogin/date versus subject/period semantics.
- `missions.mission_activations`: `id uuid PK`, `mission_definition_id`, `mission_revision_id`, `activation_sequence bigint CHECK>=1`, `activated_at`, `deactivated_at NULL`; unique `(mission_definition_id,activation_sequence)`, one filtered open interval per Mission, and composite FK proving revision ownership. Historical selection is `activated_at <= occurred_at AND (deactivated_at IS NULL OR occurred_at < deactivated_at)`. Rows cannot be deleted or rewritten; only a null `deactivated_at` may be closed once, and overlapping intervals are rejected.
- `missions.action_receipts`: `id uuid PK`, `source_event_id uuid`, `source_event_type varchar(200)`, `user_id` restrictive FK, `subject_id NULL`, `payload_fingerprint char(64)` lowercase SHA-256, `occurred_at timestamptz`, `occurred_local_date date`, `received_at timestamptz`, `processing_status` (`Pending|Processed`); unique `(source_event_id,source_event_type)`, query index `(user_id,occurred_local_date,processing_status)`, and filtered worker index `(processing_status,received_at,id) WHERE Pending`. Source events use canonical PostgreSQL microsecond precision before payload serialization. `occurred_local_date` is derived from authoritative `occurred_at` in `Asia/Ho_Chi_Minh`. Exact identity replay is a no-op only when the full typed-event fingerprint and authoritative receipt fields match; conflicting reuse fails closed. Upgrade backfills legacy M01 receipts with a deterministic legacy fingerprint without dropping rows; later delivery with unprovable full equality fails closed.
- `missions.mission_progress`: `id uuid PK`, `user_id`, `mission_revision_id`, `period_key`, `progress_count integer CHECK>=0`, `status`, `completed_at NULL`, `version`; unique `(user_id,mission_revision_id,period_key)`.
- `missions.progress_actions`: `mission_progress_id uuid FK`, `source_event_id uuid`, `subject_id uuid NULL`, `dedup_key varchar(160)`, `occurred_at`; unique `(mission_progress_id,dedup_key)`.
- `missions.reward_grants`: `id uuid PK`, `progress_id uuid UNIQUE`, `user_id`, `bonus_coins bigint CHECK BETWEEN 1 AND 300`, `outcome` Granted/DeniedDailyCap, `local_date`, `decided_at`, `wallet_operation_id NULL UNIQUE`; composite FKs enforce progress and Wallet-operation ownership. Granted requires an operation; DeniedDailyCap forbids it. Deferred database integrity requires the operation to be `MissionReward/RewardGrant`, sourced by this grant, with exactly one matching positive Bonus/Available ledger entry equal to `bonus_coins`.
- `missions.daily_counters`: composite PK `(user_id,local_date)`, `granted_total bigint CHECK BETWEEN 0 AND 300`, `version`.

## Admin and infrastructure
- `administration.audit_logs`: `id uuid PK`, `actor_id`, `action`, `target_type`, `target_id`, `correlation_id`, `occurred_at`, `redacted_changes jsonb`; append-only database trigger; indexes `(target_type,target_id,occurred_at)`, `(actor_id,occurred_at)` and descending `(occurred_at,id)`. A04 adds the last index because every Audit request filters by the leading date range and orders by `(occurred_at DESC,id DESC)`; the existing actor/target-leading indexes cannot support the unfiltered timeline.
- `administration.typed_settings`: `key varchar(100) PK`, `value_json jsonb`, `version`, `updated_at`; fixed policies (e.g. 300 cap) not writable.
- `infrastructure.outbox_messages`: `id uuid PK`, `event_type`, `payload jsonb`, `occurred_at`, `available_at`, `status`, `attempt_count`, `locked_until NULL`, `last_error_redacted NULL`; index `(status,available_at)`. An event with no registered consumer is deferred as Pending without consuming the retry budget, so a later task can register the real consumer without losing earlier integration events.
- `infrastructure.processed_messages`: composite PK `(consumer,message_id)`, `processed_at`.
- `infrastructure.idempotency_records`: unique `(actor_scope,operation_type,idempotency_key)` and request fingerprint, response/result reference, TTL policy (proposed implementation detail).
