# P0 Request/Response Contracts — Implementation Blueprint

**Status:** approved business behavior with *proposed* wire schemas. SePay checkout/QR and production-account delivery remain Verification Required; B02 webhook HMAC/payload/acknowledgement has an implemented OpenAPI contract based on official provider documentation and automated fixtures, but still requires a project-owned SePay Test-mode trace before production enablement. Cloudinary protected manifest is also Verification Required. `Idempotency-Key` required on financial POST commands. Actor scopes indicated.

## Identity — GET/PATCH `/api/v1/me` (User)
GET -> `{id,displayName,email,avatarUrl,role,status}`. PATCH request `{displayName}` updates only displayName; never provider subject/email/role. 400 invalid name, 401 no session, 403 disabled. Cookie Google OAuth only.

## Catalog & chapter access (Public/User)
GET `/api/v1/comics?search=&genre=&seriesStatus=&cursor=&limit=30` -> `{items:[{id,slug,title,coverAssetId,seriesStatus,updateSortAt,genres:[{id,name,slug}]}],nextCursor}`. Search is case-insensitive literal title search; `genre` is a genre slug; `seriesStatus` is `Ongoing|Completed|Hiatus`; default limit is 30 and valid limits are 1â€“100. Results contain only Published comics with at least one valid Published Chapter and use deterministic `(update_sort_at DESC,id DESC)` keyset pagination. `updateSortAt` is the greatest `published_at` among valid Published Chapters; if no Published Chapter exists, its internal fallback is `comic.created_at`. Admin-only Comic metadata edits update `comic.updated_at` but never affect reader update ordering. Draft, Hidden, deleted or scheduled/unpublished Chapters never contribute.

GET `/api/v1/comics/{slug}` -> `{id,slug,title,description,coverAssetId,seriesStatus,firstPublishedAt,updatedAt,genres:[{id,name,slug}],authors:[{id,name,slug:null}],translationGroups:[{id,name,slug:null}]}`; Draft/Hidden/invalid comics return 404 without private metadata.

GET `/api/v1/comics/{id}/chapters?page=1` -> `{items:[{id,chapterLabel,sortOrder,publicationStatus,accessSummary:{accessType,canRead,finalPriceCoins}}],page,pageSize:30,totalItems,totalPages}`; `page` is one-based and public page size is fixed at 30. The route returns only valid Published Chapters of a Published parent, ordered deterministically by `(sort_order,id)`. C04 provides an anonymous baseline in one batched query: effective price `0` is `Free/canRead=true`; positive effective price is `Locked/canRead=false`; `finalPriceCoins` is `chapter.price_override_coins ?? comic.default_price_coins`. R01 owns authenticated `VipIncluded`/`CoinUnlocked` enrichment and must replace this baseline without per-chapter HTTP calls. C04 never returns Chapter page/provider identifiers.

GET `/api/v1/chapters/{id}/access` -> `{chapterId,accessType:"Free|VipIncluded|CoinUnlocked|Locked|Unavailable",canRead,priceCoins,needsLogin}`. GET `/api/v1/chapters/{id}/pages` only after access check: `{chapterId,pages:[{order,width,height,deliveryUrl}],manifestIssuedAt,refreshHint}`. For R01 Free content, `deliveryUrl` is the same-origin GET `/api/v1/chapters/{id}/pages/{pageOrder}/content`, not a Cloudinary/provider URL. The content route repeats the access check, returns a supported raster image with `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`, and uses the same `401`, `403`, `404` and `503` error contract. Protected Paid/VIP delivery remains unresolved and must fail secure.

R01 implements these GET routes anonymously so Free content can be evaluated and read without login. Unpublished/Hidden/invalid content returns `404 CHAPTER_UNAVAILABLE`. A Locked anonymous manifest or content request returns `401 AUTH_REQUIRED`; a signed-in user without entitlement receives `403 FORBIDDEN`. Free manifests contain only ordered Ready pages and are `Cache-Control: no-store`. The content route fetches provider bytes internally and rechecks publication, effective price and page asset identity after the fetch, so a concurrent hide/reprice/asset replacement fails closed without returning bytes. Chapter-list enrichment retries one Catalog/Reading visibility mismatch and removes an item that is still missing, rather than exposing stale hidden metadata as `Unavailable`. Although the access evaluator supports `VipIncluded` and `CoinUnlocked` precedence, V01/U02 own their persistent production sources. Until Q02 verifies protected Cloudinary delivery, an otherwise authorized Paid/VIP manifest/content request returns `503 PROVIDER_UNAVAILABLE` instead of exposing a Free/shareable delivery path.

## Catalog publication and slug (Admin)
POST `/api/v1/admin/comics/{comicId}/publish`, POST `/api/v1/admin/comics/{comicId}/hide`, POST `/api/v1/admin/chapters/{chapterId}/publish`, and POST `/api/v1/admin/chapters/{chapterId}/hide` accept `{expectedVersion}` and return 200 `{id,publicationStatus,version,firstPublishedAt}`. PATCH `/api/v1/admin/comics/{comicId}/slug` accepts `{slug,expectedVersion}` and returns 200 `{id,slug,version}`. All routes require an authenticated Admin and CSRF token. They return 400 `VALIDATION_FAILED`, 404 `RESOURCE_NOT_FOUND`, and 409 `CONCURRENCY_CONFLICT`; publication/slug-lock invariant failures return 422 `PUBLICATION_PRECONDITION_FAILED`, while an existing slug returns 409 `SLUG_CONFLICT`. These non-financial commands use optimistic versions rather than `Idempotency-Key`. Mutations and their redacted immutable audit rows commit in the same PostgreSQL transaction.

## Reading session (User)
All session routes require an authenticated User and the global CSRF policy. POST `/api/v1/reading/sessions` accepts `{chapterId}` and returns 201 `{sessionId,startedAt,expiresAt,manifestRevision,manifestPageCount,policy:{revision,minProgressBasisPoints:9000,minActiveDurationMs:15000},version}`. The server supplies the timestamps, uses an absolute non-sliding 30-minute expiry, and creates the session only when the R01 predicate confirms a Published Comic/Chapter, at least one Ready page, and current read entitlement.

PATCH `/api/v1/reading/sessions/{id}` accepts `{currentPageOrder:int>=1,currentPageOffsetRatio:number[0,1],sequenceNumber:long>=1}` and returns 200 `{sessionId,acceptedPosition:{pageOrder?,pageOffsetRatio?},acceptedMaxProgressBasisPoints,activeDurationMs,manifestRevision,manifestPageCount,lastAcceptedSequence,expiresAt,version}`. Progress is derived from current Ready-page ordinal plus offset. Sequence begins at 1 and must increment by one; same sequence and canonical payload is an idempotent replay, while payload mismatch, stale sequence, and gap return 409 `READING_SEQUENCE_CONFLICT`. The first accepted PATCH credits no active time; subsequent accepted heartbeats credit server elapsed time up to 15 seconds each. The endpoint is limited to 60 requests/minute/User by default.

When the Ready-page revision changes, the server remaps the reported page on the current Ready set, records the new revision, and never decreases accepted maximum progress. A no-longer-Ready page cannot advance progress. If the previously accepted page disappeared, `acceptedPosition` becomes the next Ready page at offset `0`, or the previous Ready page at offset `1` if there is no following page; this remap grants neither progress nor active time. POST `/api/v1/reading/sessions/{id}/qualify` returns 200 `{qualified,qualifiedAt?,reasonCode?,version}`. Qualification requires >=9000 basis points, >=15000ms valid active time, an unexpired session, and current publication/access. Session/progress mutation and the one-time `Reading.ChapterReadQualified.v1` outbox event are committed in one transaction. Nonqualifying progress creates no Mission event.

## Library and follows (User)
All Library routes require an authenticated User; PUT/DELETE also require the global CSRF token. PUT `/api/v1/comics/{comicId}/follow` is idempotent and returns 200 for both the first insert and a replay: `{comicId,followed:true,followedAt}`. It accepts only a currently Published Comic with at least one valid Published Chapter/Ready page. The first insert and `Reading.ComicFollowed.v1` outbox event commit in one PostgreSQL transaction. DELETE on the same route is idempotent and returns 204 whether or not the follow existed. GET `/api/v1/comics/{comicId}/follow-status` returns the current User-owned state `{comicId,followed,followedAt?}` without exposing Comic metadata.

GET `/api/v1/library/following?cursor=&limit=20` returns `{items:[{comicId,availability:"Available|Unavailable",slug?,title?,coverAssetId?,seriesStatus?,followedAt}],nextCursor?}`. GET `/api/v1/library/continue?cursor=&limit=20` returns `{items:[{comicId,availability,slug?,title?,coverAssetId?,seriesStatus?,chapterId?,chapterLabel?,pageOrder?,pageOffsetRatio?,acceptedMaxProgressBasisPoints?,lastReadAt,accessType?,canRead}],nextCursor?}`. Both use an opaque 32-character keyset cursor, default `limit=20`, range `1..50`, and return 400 `VALIDATION_FAILED` for an invalid cursor/limit. `reading_progress`, not the 30-minute ReadingSession, is the authoritative Continue source; R02 updates its accepted maximum progress in the same transaction as the accepted heartbeat. Followed or progress rows remain owned by the User, but if publication/readiness is no longer valid the response uses `Unavailable` and redacts Comic/Chapter/page/progress metadata. Continue rechecks current entitlement; a no-longer-Ready saved page is remapped to the next Ready page at offset 0, or the previous Ready page at offset 1, and no position is returned when access is not currently allowed.

## Wallet (User)
Both routes require an authenticated User and return only the current user's data with `Cache-Control: no-store`. GET `/api/v1/wallet` lazily creates an idempotent zero-balance wallet when none exists and returns `{paidAvailable,paidReserved,bonusAvailable,totalAvailable,version}`; `totalAvailable` excludes reserved Paid Coins. GET `/api/v1/wallet/entries?cursor=&limit=30` returns `{items:[{id,operationId,operationType,sourceType,sourceId,coinType,bucket,deltaCoins,occurredAt}],nextCursor}` in `(occurredAt DESC,id DESC)` order. The cursor is an opaque 32-character token; `limit` defaults to 30 and must be 1..100. Ledger rows are immutable and other users' data is never exposed.

## Unlock Quote (User)
POST `/api/v1/chapters/{id}/unlock-quotes` requires an authenticated User and CSRF token and accepts no client-owned pricing input. It is limited to 10 requests/minute/authenticated User and returns 201 `{quoteId,chapterId,basePriceCoins,vipDiscountApplied,finalPriceCoins,bonusToSpend,paidToSpend,expiresAt,priceRevision}`. The server derives every pricing field and persists an immutable quote for exactly 5 minutes, bound to the User, Chapter, base/final price, VIP discount and canonical pricing-policy revision. Example price 101 with active-VIP discount -> ceil(80.8)=81. `bonusToSpend` then `paidToSpend` are estimates capped by the currently available balances; their sum may be below `finalPriceCoins`. A quote never reserves or debits funds and is not proof of entitlement. Only Locked chapters can be quoted; Free, VipIncluded or CoinUnlocked access returns 409 `ALREADY_UNLOCKED`, while unpublished/invalid content returns 404 `CHAPTER_UNAVAILABLE`. Runtime responses are 201, standardized 400/401/403/404/409, and standardized 429 `RATE_LIMITED`. Expired quotes remain immutable audit/replay snapshots for 30 days after `expiresAt`; after that time an unreferenced quote may be deleted by a future cleanup process. U01 does not add that worker, and U02 must protect consumed/referenced quotes with a restrictive relationship.

## Unlock (User)
POST `/api/v1/chapters/{id}/unlock` requires an authenticated User, CSRF token and `Idempotency-Key` (1..200 characters), accepts only `{quoteId}`, and returns 200 `{chapterId,accessType:"CoinUnlocked",spent:{bonusCoins,paidCoins,totalCoins},walletAfter:{paidAvailable,bonusAvailable},alreadyUnlocked}` with `Cache-Control: no-store`; the response schema restricts `accessType` to that single literal. A committed same-key/same-Chapter/quote result is loaded before mutable quote or Wallet validation, so replay remains deterministic after quote expiry/retention changes or later Wallet drift and never repeats debit/outbox work. Same key with another payload returns 409 `IDEMPOTENCY_CONFLICT` even when the supplied quote is absent.

For a new request, the PostgreSQL lock order is Wallet, Paid lots FIFO, per-User VIP advisory key, quote, Chapter, Comic, then Chapter pages. Only after all decision-bearing locks are held does the transaction sample `clock_timestamp()` and recheck quote ownership/expiry, current publication/Ready-page access, VIP expiry/discount, current canonical price revision, reconciled Wallet/ledger/lots and available balance. It consumes Bonus before non-reserved Paid lots ordered `(createdAt,id)`, appends the Wallet operation/entries/allocations, inserts exactly one immutable `chapter_unlock`, and writes `Reading.ChapterUnlocked.v1` before one commit. A deferred database integrity guard requires the referenced operation to be `ChapterUnlock/ReadingUnlock` sourced by that entitlement and requires debit-ledger and Paid-allocation totals to match its spend snapshot. A different key cannot double debit and returns the existing entitlement with `alreadyUnlocked=true`. Runtime errors are standardized 400/401/403/404, 409 `QUOTE_EXPIRED|PRICE_CHANGED|ALREADY_UNLOCKED|IDEMPOTENCY_CONFLICT|CONCURRENCY_CONFLICT`, and 422 `INSUFFICIENT_COINS`. Hidden/unpublished/invalid content is 404. Client fields cannot override price, spend split, Wallet snapshot, timestamps or entitlement state.

## TopUp (User)
POST `/api/v1/billing/topups`, authenticated User + CSRF + required `Idempotency-Key` (1–200 characters), `{amountVnd:100000}` -> 201 `{orderId,orderCode,amountVnd:100000,paidCoinsExpected:10000,status:"Pending"|"Expired"|"Succeeded",expiresAt,paymentInstructions:{type:"ProviderSpecific"}}`. Validate 10k–2m VND, multiple 1000. The server creates `createdAt` from PostgreSQL time after entering the idempotency critical section and calculates `expiresAt = createdAt + Billing:TopUpOrderTtlMinutes`; configuration defaults to 30 minutes, must be positive, and is validated at startup. The request has no expiry field. When a Pending order is processed at or after `expiresAt`, the server persists the monotonic transition to `Expired` with `expiredAt`; clock rollback cannot return it to Pending. Idempotency scope is `(User, TopUp, Idempotency-Key)`: the same canonical amount replays the original order, including its later Expired or Succeeded state, while a different amount returns 409 `IDEMPOTENCY_CONFLICT`; a new operation requires a new key. Create is limited to 10 requests/minute/authenticated User and returns standardized 429 `RATE_LIMITED`. `paymentInstructions` remains a **provider-neutral placeholder** until actual SePay QR/checkout is verified. Redirect alone never fulfills.

## SePay webhook (Provider)
POST `/api/v1/webhooks/sepay/ipn` is an anonymous provider callback and accepts `application/json` only. Required headers are `X-SePay-Timestamp` (canonical Unix seconds) and `X-SePay-Signature` (`sha256=` plus 64 hexadecimal characters). The signature is HMAC-SHA256 over the exact UTF-8 bytes `{timestamp}.{rawBody}`. The timestamp tolerance defaults to 300 seconds, body limit to 65,536 bytes, and remote-address rate limit to 120 requests/minute; all are server-configurable. The adapter is disabled by default and startup validation requires a 32-500 character secret and expected receiving account when enabled.

The payload fields consumed by B02 are `{id:integer>0,gateway:string,transactionDate:"yyyy-MM-dd HH:mm:ss",accountNumber:string,code?:string,content:string,transferType:"in"|"out",transferAmount:integer>0,accumulated?:integer>=0,referenceCode?:string}`. `id` is the stable provider transaction identity. Authenticated valid input receives HTTP 200 `{success:true}` for first delivery, exact replay, and reconciliation-required evidence so provider retries do not become financial side effects. Invalid/missing signature or stale timestamp returns 401 `{success:false}`; malformed input returns 400; oversized input 413; rate limit 429; disabled adapter 503. No user-facing ProblemDetails contract is implied for this provider callback.

B02 verifies raw-body HMAC and receiving account, normalizes direction/amount/timestamp, persists one provider transaction plus delivery evidence atomically, and deduplicates on `(SePay,id)`. B03 matches `code` exactly to a PaymentOrder `orderCode`; B03 fulfills TopUp and V01 extends the same atomic flow for VipPurchase. A still-Pending order is auto-fulfilled only when PostgreSQL `clock_timestamp()` sampled after the required locks is strictly before `expiresAt`, `transferAmount` exactly equals `amountVnd`, and no success artifact or integrity drift exists. TopUp commits order/provider status, Wallet Paid credit, one PaidCoinLot, immutable `TopUpCredit` ledger operation/entry and `Billing.WalletTopUpCompleted.v1` together. VipPurchase commits order/provider status, one append-only VIP transaction, the serialized subscription extension and `Membership.VipMembershipActivated.v1` together. Any invariant drift produces durable `FULFILLMENT_STATE_CONFLICT` with zero new fulfillment mutation.

At or after expiry, processing persists `Expired` plus provider reconciliation reason `LatePayment` and performs no financial or membership success write. Provider `transactionDate`/`occurredAt` is evidence only and never overrides processing-time expiry. Unknown code, amount mismatch, unsupported order type, already-fulfilled order, wrong account/direction or missing code is retained as reconciliation evidence and acknowledged with HTTP 200. Exact replay records a Duplicate delivery but returns the same authoritative fulfilled/reconciliation outcome without another credit or VIP period. Actual Test-mode delivery and retry traces for the project account remain **Verification Required** before production enablement.

## VIP (User/Admin)
GET `/api/v1/membership/plan` -> `{planId,priceVnd,durationHours:720,discountPercent:20,version}`. GET `/api/v1/membership/me` -> `{isActive,expiresAt:null|date-time}`. POST `/api/v1/membership/checkout`, authenticated User + CSRF + required `Idempotency-Key` (1-200 characters), `{planId:uuid}` -> 201 `{orderId,amountVnd,durationHours:720,status:"Pending"|"Expired"|"Succeeded",expiresAt,paymentInstructions:{type:"ProviderSpecific"}}`. Checkout is limited to 10 requests/minute/authenticated User.

For a new order, the server acquires the idempotency and VIP-plan snapshot locks before sampling PostgreSQL time, then sets `expiresAt = createdAt + Membership:VipOrderTtlMinutes`; the default is 30 minutes, must be positive, and is startup-validated independently of the TopUp TTL. The request has no expiry field. A Pending order processed at/after expiry is persisted Expired and never returns to Pending. Idempotency scope is `(User,VipPurchase,Idempotency-Key)`: the same canonical plan replays the original current order state, including Expired or Succeeded; a different plan returns 409 `IDEMPOTENCY_CONFLICT`; a new logical purchase requires a new key.

Successful provider fulfillment atomically extends `max(currentExpiry,fulfilledAt)+720h`, increments authoritative `VipSubscription.Version`, records exactly one VIP transaction with the same consecutive `SubscriptionVersion`, and emits one activation outbox event. The complete version/expiry chain is validated before mutation; latest ordering never depends on timestamps or GUIDs. Late or mismatched provider evidence is retained for reconciliation without creating/extending membership; provider `OccurredAt` cannot bypass expiry. GET `/api/v1/admin/vip-plan` returns the same plan schema. PATCH `/api/v1/admin/vip-plan` with `{priceVnd:integer>0,expectedVersion:integer>=1}` changes **future-order price only**, returns the updated plan, and uses 409 `CONCURRENCY_CONFLICT` for a stale version. Duration/discount remain fixed for MVP.

## Refund eligibility (User)
GET `/api/v1/refunds/eligibility?paymentOrderId={id}` requires authenticated User and returns `{orderId,originalAmountVnd,feeVnd,netRefundVnd,lotGrantedCoins,lotAvailableCoins,eligible,reasonCode,paidAt}`. Informational snapshot only; lot is rechecked when Admin approves. The server uses PostgreSQL time and permits requests through `paidAt + 7 days`; the 5% fee is a whole VND amount because TopUps are multiples of 1,000. A non-owned/missing order is 404; a non-fulfilled/non-TopUp order or missing authoritative original lot is 422 `REFUND_ORDER_NOT_ELIGIBLE`.

## Refund request (User)
POST `/api/v1/refunds`, authenticated User + CSRF + required `Idempotency-Key` (1-200 characters), `{paymentOrderId,reason,recipient:{bankCode,accountNumber,accountHolder}}` -> 201 `{refundId,status:"Requested",originalAmountVnd,feeVnd,netRefundVnd,requestedAt}`. `reason` is 1..1000 characters; recipient constraints are `bankCode` 2..32, `accountNumber` 4..34 and `accountHolder` 2..120. Unknown JSON fields are rejected. Creation is limited to 10 requests/minute/authenticated User. The canonical request is persistently idempotent: same User/key/payload replays the original 201 result; different payload returns 409 `IDEMPOTENCY_CONFLICT`. The persisted fingerprint is a versioned HMAC-SHA256 made with a refund-only application secret; it is not an unkeyed digest or a Data Protection key. Retained historical HMAC versions allow old requests to replay during key rotation. Recipient account number and holder are encrypted before persistence under an explicit application protection version; only bank code and masked derivatives are returned or logged. One RefundRequest per TopUp **even if Rejected**; another key returns 409 `REFUND_ALREADY_EXISTS`. The original fulfilled TopUp and its exact PaidCoinLot are locked and checked against authoritative PostgreSQL time, but RF01 creates no Wallet reservation or ledger mutation. The request-time snapshot and recipient row are immutable after creation; RF02/RF03 must use the separate authoritative financial-processing loader rather than presentation list/detail data.

GET `/api/v1/refunds` returns at most the latest 100 requests owned by the current User, newest first. GET `/api/v1/refunds/{refundId}` returns one owned request or 404. Detail/list items are `{refundId,paymentOrderId,status,reason,originalAmountVnd,feeVnd,netRefundVnd,requiredRecoveryCoins,requestedAt,recipient:{bankCode,accountNumberMasked,accountHolderMasked}}`; ciphertext/plain recipient fields are never returned. Refund create may return standardized 400/401/403/404/409/422/429 errors.

## Refund Admin transitions
All routes require authenticated Admin authorization and CSRF, return `Cache-Control: no-store`, use standardized errors, and share a 20 mutation requests/minute/Admin rate limit with 429 `RATE_LIMITED`. The transition response is `{refundId,status,requiredRecoveryCoins,version,reviewedBy?,reviewedAt?,approvedBy?,approvedAt?,decisionReason?,reservationId?,walletOperationId?}`.

`POST /api/v1/admin/refunds/{id}/review` -> 200 `UnderReview`; exact retry while already UnderReview is a no-op. Only `Requested` may enter review.

`POST /api/v1/admin/refunds/{id}/approve`, required `Idempotency-Key` header (1..200), body `{expectedVersion,decisionNote}` -> 200 `RecoveryReserved`. Approval locks `Wallet -> exact original PaidCoinLot -> RefundRequest`, then uses PostgreSQL time and revalidates the fulfilled TopUp, immutable snapshot, protected recipient, full untouched original lot and Wallet/lot/ledger reconciliation. It atomically moves all granted coins from Paid Available to Paid Reserved, increments the exact lot's reservation, inserts one `CoinReservation`, appends the two immutable ledger legs, transitions the request and writes Admin audit. Same Admin/key/canonical approval replays the persisted response; another payload returns 409 `IDEMPOTENCY_CONFLICT`. Stale version is 409 `CONCURRENCY_CONFLICT`; invalid lifecycle is 409 `REFUND_STATE_CONFLICT`; integrity drift is 409 `FINANCIAL_INTEGRITY_CONFLICT`; insufficient original recovery is 422 `REFUND_RECOVERY_INSUFFICIENT` with zero partial mutation.

`POST /api/v1/admin/refunds/{id}/reject` `{expectedVersion,reason}` -> 200 `Rejected` and audit, with no Wallet/lot/ledger/reservation mutation. Only `UnderReview` may be approved or rejected.
`POST /transfer-attempts` records manual attempt details/reference/evidence and state, does **not** itself prove bank succeeded.
`POST /complete` `{expectedVersion,transferRecordId,confirmationNote}` -> Completed only after verified/reviewed bank evidence; consumes reserved to refunded, immutable ledger. `POST /release` after **confirmed failed** transfer -> release to Paid available; ambiguous `NeedsReconciliation` holds reservation. Never automatically retry bank payout.

## Missions (User/Admin)
All user Mission routes require the User policy, return `Cache-Control: no-store`, and may return standardized 401/403 errors. **No User API grants or claims its own reward.**

- GET `/api/v1/missions` -> 200 array `{missionId,revisionId,code,name,description,actionType,cycleType,periodKey,targetCount,progressCount,rewardBonusCoins,progressStatus,rewardStatus,effectiveFrom,effectiveUntil?}` for current active definitions whose current revision is in its effective window. `progressStatus` is `InProgress|Completed`; `rewardStatus` is `Pending|Granted|DeniedDailyCap`.
- GET `/api/v1/missions/daily-limit` -> 200 `{localDate,limitCoins:300,grantedCoins,remainingCoins}` for the current `Asia/Ho_Chi_Minh` date.
- GET `/api/v1/missions/rewards?cursor&limit=30` -> 200 `{items,nextCursor?}`. `limit` is 1..100; cursor is an opaque 32-character keyset cursor. Each item is `{rewardGrantId,missionId,revisionId,missionName,outcome,rewardBonusCoins,grantedBonusCoins,localDate,decidedAt}`. Invalid cursor/limit returns 400 `VALIDATION_FAILED`.

M01 Admin routes all require Admin authorization. Unsafe requests require the authenticated antiforgery header/cookie pair and share a fixed-window limit of 20 mutation requests/minute/Admin, partitioned by authenticated Admin user ID. GET routes do not consume that policy. A rejected mutation returns standardized 429 `RATE_LIMITED`. Responses use the standard error schema `{errorCode,message,traceId}` in addition to Problem Details fields. Request enums accept only the documented string literals; numeric enum values return 400 `VALIDATION_FAILED`.

- GET `/api/v1/admin/missions` -> 200 array of Mission definitions with their append-only revisions; 401/403.
- GET `/api/v1/admin/missions/{missionId}` -> 200 definition or 404 `MISSION_NOT_FOUND`; 401/403.
- POST `/api/v1/admin/missions` body `{code,name,description,actionType,cycleType}` -> 201 definition; 400 `VALIDATION_FAILED`, 409 `MISSION_CODE_CONFLICT`, 401/403, 429. `actionType` is `DailyLogin|ChapterReadQualified|ComicFollowed|ChapterUnlocked|WalletTopUpCompleted`; `cycleType` is `Fixed|Daily|Weekly|Event`.
- POST `/api/v1/admin/missions/{missionId}/revisions` body `{targetCount,rewardBonusCoins,repeatPolicy,effectiveFrom,effectiveUntil?,configurationSnapshot}` -> 201 revision; 400/404/409 `MISSION_STATE_CONFLICT`, 401/403, 429. Reward is 1..300, dates are authoritative UTC inputs with a half-open window, configuration is a JSON object, and repeat policy is `OncePerVietnamDate|UniqueSubjectPerPeriod` consistent with the action.
- POST `/api/v1/admin/missions/{missionId}/activate` body `{revisionId,expectedVersion}` -> 200 definition; 400/404/409 `CONCURRENCY_CONFLICT|MISSION_STATE_CONFLICT`, 401/403, 429.
- POST `/api/v1/admin/missions/{missionId}/deactivate` body `{expectedVersion}` -> 200 definition; 400/404/409 `CONCURRENCY_CONFLICT`, 401/403, 429.

`ActiveRevisionId` is the authority for current Admin/UI state. Receipt progress uses immutable activation history at event time with `[ActivatedAt,DeactivatedAt)` semantics. A receipt with no matching history is processed without progress and never falls back to the current revision. An out-of-window historical revision is ineligible. Backend event -> deduplicated ActionReceipt is M01; atomic progress/reward decision, Bonus Wallet ledger, outbox and daily cap are M02.

## Error conventions
Errors expose normalized `{errorCode,message,traceId}` fields in addition to standard Problem Details fields. Use `docs/api/error-codes.md` for HTTP mapping and domain guard. Financial request idempotency stores request fingerprint, prior result and in-progress state. For same-key operation executing, default `409 OPERATION_IN_PROGRESS` + Retry-After unless durable status resource introduced by approved ADR.
